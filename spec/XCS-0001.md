# XCS-0001: Credential Schema and Verification Protocol

Status: Alpha
Category: Ecosystem
Version: 0.1

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHOULD**, and **MAY** are to be interpreted as described in BCP 14 when, and only when, they appear in all capitals.

## 1. Purpose

XCS coordinates reusable schemas for native XRPL Credential ledger objects. It does not replace the XRPL Credential lifecycle, define a universal issuer registry, or put claim data on-ledger.

An implementation verifies four independent dimensions:

1. the native Credential state;
2. the referenced XCS schema;
3. the integrity and schema conformance of the payload;
4. application-specific trust in the issuer.

No dimension implies another.

The JSON Schema files shipped with this specification are non-exhaustive structural aids. They do
not express every protocol rule, including strict JSON parsing, UTF-8 byte limits, aggregate
descriptor and depth limits, inheritance, or cross-field constraints. This document and conforming
protocol validators determine validity; passing a JSON Schema check alone is not sufficient.

## 2. Network profile

Every XCS deployment MUST publish an immutable profile for each XRPL network/reset:

```json
{
  "profileId": "xrpl-testnet-xcs-v0.1-example",
  "xcsVersion": "0.1",
  "networkId": 1,
  "requiredAmendment": "1CB67D082CF7D9102412D34258CEDB400E659352D3B207348889297A6D90F5EF",
  "registryAddress": "r...",
  "registrationAmountDrops": "1",
  "activationLedgerIndex": 123,
  "activationLedgerHash": "0123..."
}
```

`profileId` is a lowercase stable identifier matching `[a-z0-9][a-z0-9._-]{0,127}`. `networkId` and transaction indices are unsigned 32-bit integers; `activationLedgerIndex` is a strictly positive unsigned 32-bit integer. Hexadecimal profile inputs are case-insensitive, then `requiredAmendment` is normalized to uppercase and `activationLedgerHash` to lowercase. `registryAddress` is a checksummed XRPL classic address. Endpoint URLs are deployment configuration and MUST NOT alter the profile identity. For a given `profileId`, every published profile field is immutable. A network reset or any changed profile field requires a new `profileId` and activation boundary; implementations MUST NOT reinterpret or edit the prior profile in place.

An indexer MUST ignore events preceding the activation ledger and MUST stop if that ledger hash or any later parent link does not match. It MUST verify the required amendment before declaring itself ready.

## 3. Schema registration

A registration is a validated `Payment` transaction satisfying all of these conditions:

- `meta.TransactionResult` is `tesSUCCESS`;
- `Destination` equals the profile registry;
- `Amount` is the exact native XRP string from `registrationAmountDrops`;
- partial payment, paths, `SendMax` and delivered issued currency are absent;
- exactly one memo decodes to `MemoType = xcs:schema_register`;
- that memo decodes to `MemoFormat = application/json`;
- its `MemoData` is the UTF-8 encoding of the exact JCS form of a valid schema.

XRPL memo fields are hexadecimal blobs. Non-XCS memos MAY coexist and are ignored. Builders MUST
apply the XRPL 1 KiB memo limit to the serialized objects inside the `Memos` array, exactly as
`rippled` does: the count includes each `Memo` field header, its fields and its object terminator,
but excludes the outer `Memos` field header and array terminator. Builders MUST reject a transaction
when that count exceeds 1,024 bytes.

The transaction `Account` is the schema publisher. Registration is permissionless. Paying the registry does not create endorsement.

### 3.1 Schema object

The only top-level properties are:

| Property      | Required | Meaning                                  |
| ------------- | -------: | ---------------------------------------- |
| `xcsVersion`  |      yes | Exact string `0.1`                       |
| `name`        |      yes | Human name, 1–64 UTF-8 bytes             |
| `description` |      yes | Human description, 1–256 UTF-8 bytes     |
| `fields`      |      yes | Non-empty map of names to descriptors    |
| `extends`     |       no | One prior valid schema UID               |
| `supersedes`  |       no | Prior schema UID from the same publisher |

Unknown properties, duplicate JSON keys, invalid Unicode scalar sequences, control characters in human text and non-canonical bytes make the registration invalid.

A field name MUST match `[A-Za-z_][A-Za-z0-9_]{0,63}`. A field descriptor contains `type` and optional `optional`; `optional` defaults to `false`. A registration MAY contain an explicit `"optional": false`; the parsed schema is normalized by omitting it before UID computation and storage. `array` additionally contains `items`; `object` additionally contains `fields`. No other descriptor property is allowed.

Supported types and JSON representations:

| Type      | Representation                                  |
| --------- | ----------------------------------------------- |
| `string`  | Valid Unicode JSON string                       |
| `bool`    | JSON boolean                                    |
| `uint`    | Canonical decimal string in `[0, 2^256-1]`      |
| `int`     | Canonical decimal string in `[-2^255, 2^255-1]` |
| `bytes`   | Unpadded base64url string                       |
| `address` | Canonical XRPL classic address                  |
| `array`   | JSON array whose elements match `items`         |
| `object`  | JSON object whose fields match `fields` exactly |

`null` is never valid. A non-optional field is required. Undeclared properties are invalid at every object level. Every `fields` map MUST be non-empty. Type nesting and inheritance depth are limited to 16.

A locally declared or resolved schema MUST contain at most 256 descriptor nodes in total. Each
named field descriptor counts once, including every nested object field, and each `array.items`
descriptor counts once. The `fields` maps themselves do not count.

`extends` MUST reference a valid, earlier schema on the same network. The child only adds fields; redefining an inherited field is invalid. `supersedes` records lineage only and MUST NOT affect resolution. Multiple inheritance, exclusions and future references are not supported in v0.1.

## 4. Schema UID

Once the registration ledger is validated, the UID is:

```text
SHA-256(UTF8(JCS({
  "purpose": "xcs.schema.uid",
  "version": "0.1",
  "networkId": profile.networkId,
  "ledgerHash": lowercase(ledger.hash),
  "ledgerIndex": ledger.index,
  "transactionIndex": metadata.TransactionIndex,
  "publisher": transaction.Account,
  "schema": parsedSchema
})))
```

The display form is 64 lowercase hexadecimal characters. The native `CredentialType` is the 32 digest bytes; XRPL JSON represents those bytes as 64 hexadecimal characters. Implementations compare bytes, not display casing.

Invalid registrations have an audit identity but no usable XCS schema UID. A valid schema is never reinterpreted by a later implementation version.

## 5. Credential payload

An XCS Credential MUST contain a non-empty native `URI` whose UTF-8 bytes decode to one of the formats below. The retrieved bytes MUST be canonical JCS for this exact envelope:

```json
{
  "xcsVersion": "0.1",
  "issuer": "r...",
  "subject": "r...",
  "schema": "64-lowercase-hex",
  "claims": {}
}
```

The envelope issuer, subject and schema MUST match the native Credential. `claims` MUST validate against the resolved schema.

Supported URI forms:

- `ipfs://<CIDv1>` where the CID uses the raw codec and a SHA-256 multihash of the exact JCS bytes, with no path, query or fragment;
- an HTTPS URL ending in the sole fragment `#xcs-sha256=<64 lowercase hex>`, where the digest covers the exact JCS bytes and the fragment is removed for retrieval.

The raw HTTPS URI MUST begin with the literal lowercase prefix `https://`. It MUST NOT contain an
ASCII control or whitespace character or a backslash. Its raw authority component, ending at the
first `/`, `?`, `#`, or the end of the URI, MUST be non-empty and MUST NOT contain `@`; therefore a
userinfo component is forbidden even when its username and password are empty. Implementations MUST
apply these checks before URL-parser normalization.

The UTF-8 URI MUST fit the native 256-byte field and the payload MUST NOT exceed 1 MiB. Other schemes are non-conforming.

Retrieval failure is `unavailable`; a digest mismatch is `tampered`; invalid JCS, envelope linkage or claims are `invalid`. These outcomes MUST remain distinguishable.

## 6. Native lifecycle projection

An XCS Credential is a native Credential whose `CredentialType` resolves to a prior valid schema and whose URI has a supported integrity form. Any account MAY issue against any valid schema.

The current state is:

- `pending`: object exists, is not accepted, and is not expired;
- `active`: object exists, is accepted, and is not expired;
- `expired`: object exists and its Ripple-epoch expiration is reached at validated-ledger close time;
- `deleted`: object no longer exists.

Self-issued Credentials are accepted on creation. Each creation transaction hash is a new `generationId`, including recreation of the same native object key.

An indexer MUST inspect all `AffectedNodes` in every validated transaction. It MUST NOT require a lifecycle memo or filter mutation extraction to `tesSUCCESS`, because `tecEXPIRED` and `AccountDelete` can remove Credential objects.

Deletion causes are best-effort projections: `issuer_revoked`, `subject_rejected`, `subject_removed`, `expired_cleanup`, `account_deleted`, or `self_deleted`. They describe observed actors and prior state, not unprovable intent.

## 7. Verification and trust

A report exposes `onChain`, `schema`, `payload`, and `issuerTrust` separately. A verifier MUST NOT describe a Credential as trusted solely because it is active and payload-valid.

Trust policy is outside the consensus protocol. Applications MAY use local address allowlists, an account Domain linked to `xrp-ledger.toml`, or optional catalogs. No publisher permission or global issuer directory is implied.

## 8. Errors and versioning

Protocol-library machine interfaces use these stable uppercase codes:

- JSON and canonicalization: `JSON_INVALID`, `JSON_DUPLICATE_KEY`, `JSON_INVALID_UNICODE`, `JSON_NON_IJSON_NUMBER`, and `CANONICALIZATION_UNSUPPORTED_VALUE`;
- primitives and profiles: `HEX_INVALID`, `UTF8_INVALID`, and `NETWORK_PROFILE_INVALID`;
- schemas: `SCHEMA_INVALID`, `SCHEMA_PARENT_NOT_FOUND`, `SCHEMA_PARENT_NOT_PRIOR`, `SCHEMA_PARENT_NETWORK_MISMATCH`, `SCHEMA_OVERRIDE_FORBIDDEN`, `SCHEMA_INHERITANCE_CYCLE`, `SCHEMA_DEPTH_EXCEEDED`, `SCHEMA_FIELD_LIMIT_EXCEEDED`, `SCHEMA_SUPERSEDES_NOT_FOUND`, `SCHEMA_SUPERSEDES_NOT_PRIOR`, and `SCHEMA_SUPERSEDES_PUBLISHER_MISMATCH`;
- UIDs, claims, payloads, and time: `UID_INPUT_INVALID`, `CLAIMS_INVALID`, `PAYLOAD_INVALID`, `PAYLOAD_URI_INVALID`, and `RIPPLE_TIME_INVALID`.

SDK, CLI, API, and indexer layers MAY expose additional scoped operational codes. Such codes do not change protocol validity. An indexer continuity failure is reported distinctly, including `LEDGER_BEFORE_ACTIVATION`, `ACTIVATION_HASH_MISMATCH`, `LEDGER_GAP`, or `LEDGER_PARENT_MISMATCH`.

Validity outcomes and protocol error codes are normative. Error messages, paths and additional
details are diagnostic and MAY differ between conforming implementations; consumers MUST NOT use
them as interoperability keys.

Any future change that alters schema validity, UID bytes, payload interpretation or lifecycle projection requires a new protocol version and activation profile. Versions coexist; no historical schema is silently upgraded.
